## Finding 1: ObjectKeys.requireValid rejects keys that already exist in the repo, and it guards every ObjectStorage method
- **Severity:** High
- **Location:** Phase 2, section "ObjectKeys" (key rules: lowercase only). Phase 3, section "SupabaseObjectStorage" (input validation shared by all methods).
- **Flaw:** Phase 3 runs `ObjectKeys.requireValid(key)` on `put`, `delete`, `publicUrl`, `signedDownloadUrl` and `signedUploadUrl`. Phase 2 rejects any uppercase character and tests that `"A/b"` is rejected. content-service already seeds media keys with uppercase letters. `requireValid` is meant for server-generated keys, but Phase 3 applies it to every key the library touches, including keys that were not generated by it.
- **Failure scenario:** content-service adopts `ObjectStorage` for admin replace or delete of media.
  - `delete("media","listening/demo/numM.mp3")` throws `IllegalArgumentException` before any network call.
  - `signedDownloadUrl` and `publicUrl` fail the same way for these three keys.
  - The old objects can never be cleaned up through the module. Anyone who works around it adds a second, parallel storage code path, which is the duplication the module exists to prevent.
  - The same applies to anything uploaded by hand in Dashboard before the "no manual upload" decision. Plan.md says the `media` bucket already exists, so its content is unknown.
- **Evidence:**
  - Seeded keys with uppercase `M`: `listening/demo/numM.mp3`, `listening/demo/spellM.mp3`, `listening/demo/trapM.mp3`. Found by grepping `services/content-service/src/main/resources/db`. The seed `V12__seed_listening_demo.sql` includes `numM.mp3` and `spellM.mp3`; the file with `trapM.mp3` was not identified.
  - `services/content-service/src/main/java/com/ieltspath/content/domain/vo/MediaReferencePolicy.java:18` allows `[A-Za-z0-9]`, so the existing production contract is mixed-case.
  - Plan: phase-02 test list, `"A/b"` (chữ hoa) is rejected. Phase-03, "Kiểm tra đầu vào chung cho mọi phương thức".
- **Suggested fix:** Split validation into a strict `ObjectKeys.requireGenerated` (used on `put` and on `isOwnedBy`) and a permissive "safe path" check (no `..`, no `%`, no control characters, allowed charset superset of MediaReferencePolicy) for `delete`, `publicUrl` and `signedDownloadUrl`. Add a test that all seeded keys pass the permissive check.

## Finding 2: Nothing in the module can prove an object exists, and nothing can clean up orphans, yet the plan hands the DB-vs-storage consistency problem to three services
- **Severity:** High
- **Location:** Plan.md "Quyết định" (centralised orphan cleanup deferred). Phase 1 `ObjectStorage` interface (5 methods; no exists/head/list/prefix-delete). Phase 2 `isOwnedBy`. Phase 3 "Không retry" note.
- **Flaw:** `isOwnedBy` checks only the string shape `speaking/<userId>/<file>`. It cannot tell whether the object was uploaded. The interface has no `exists`, `list`, `move` or `deleteByPrefix`, so a service cannot validate a client-supplied key or sweep leftovers.
- **Failure scenario 1 (phantom reference):**
  - A learner posts `audioReference = "speaking/<own-uuid>/<random-uuid>.webm"` without uploading anything.
  - `isOwnedBy` returns true, and the use case persists it.
  - The DB CHECK on `learner_submissions` (SPEAKING requires `audio_reference IS NOT NULL`) is satisfied.
  - The grader or examiner later requests a signed URL for a non-existent object and fails.
  - Nothing records that the submission is unusable.
- **Failure scenario 2 (orphan on retry):**
  - The mobile client uploads (put succeeds, response lost or timeout).
  - The plan's guidance is "retry means a new key", which orphans the first object.
  - The submit step is idempotent by `(user_id, submission_key)`. `CreateLearnerSubmissionUseCase.execute` returns the existing row and silently ignores the new `audioReference`. The second upload is orphaned in a private bucket forever, and nobody can find it.
- **Failure scenario 3 (avatar swap):** the avatar flow is put new, update DB, delete old. A failure between steps leaves orphans or a profile pointing at a deleted file, and the plan gives no ordering rule.
- **Evidence:**
  - `services/assessment-service/src/main/java/com/ieltspath/assessment/application/usecase/CreateLearnerSubmissionUseCase.java:30-31` (`existing.orElseGet(...)`; `audioReference` is ignored when a row exists).
  - `services/assessment-service/src/main/resources/db/migration/V1__create_assessment_tables.sql:59-65` (varchar(500), CHECK only on null-ness, no FK or existence guarantee).
  - Phase 3 Risk: "caller muốn retry thì sinh key mới".
  - Plan.md line 30: orphan cleanup is only for a possible future service.
- **Suggested fix:** Add `boolean exists(bucket,key)` (the HEAD or `object/info` endpoint) and `deleteByPrefix` or `list` to the interface, or explicitly document in the plan the required service-side protocol (head-before-persist, delete-on-DB-failure, and a scheduled reconciliation). As written, the plan cannot be implemented safely by the three services.

## Finding 3: Hard fail-fast on missing Supabase config contradicts the repo's graceful-degradation convention, and it can take down user-service (auth) and crash-loop in Docker
- **Severity:** High
- **Location:** Plan.md "Cấu hình" (fail-fast, no default for the secret). Phase 1 `SupabaseStorageProperties` and `CommonStorageAutoConfiguration`. Plan.md rule 7 (no Docker or config-repo edits).
- **Flaw:**
  - Existing optional integrations use `${X:}` with an empty default so the feature degrades and the service still boots. CLAUDE.md documents this: a missing LLM config returns 503 for essays and "phần khác vẫn chạy".
  - Storage fail-fast is only safe when the flag is false. A service that sets `app.storage.enabled=true` in config-repo but runs where `SUPABASE_*` is unset (a developer machine, CI, a Docker stack) refuses to boot.
  - user-service hosts login, so a missing avatar-storage secret can take down authentication.
  - Compose passes only the explicitly listed vars. No `SUPABASE_*` is passed to user, assessment or content, and rule 7 forbids this plan from adding them. No other plan or `blocks` entry is recorded as owning that change.
- **Failure scenario:**
  - A service plan flips `enabled: true` in config-repo.
  - `docker compose up` starts user-service without `SUPABASE_URL` or `SUPABASE_SECRET_KEY`.
  - Binding throws, the container exits, and `restart: unless-stopped` restarts it in a loop until the healthcheck budget (18 retries × 10s) is exhausted.
  - Login is down because of an avatar feature.
  - Rotating the secret needs a restart of three services. `/actuator/refresh` is exposed, but the `RestClient` bakes the key into default headers at construction and the properties bean is not refresh-scoped.
- **Evidence:**
  - `docker-compose.yml:8` (`restart: unless-stopped`), `docker-compose.yml:10-16` (healthcheck, retries 18).
  - `docker-compose.yml:153` and `docker-compose.yml:212-215` (the existing pattern is `${X:-}` defaults).
  - `infra/config-server/config-repo/assessment-service.yaml:26-28` (`${ASSESSMENT_LLM_API_KEY:}`).
  - `infra/config-server/config-repo/application.yaml` (`include: health,info,refresh`).
  - `CLAUDE.md:47-49` (the LLM degradation convention).
  - No `SUPABASE` string exists in compose or config-repo; the grep for `SUPABASE` found only plan files and `third_party`.
- **Suggested fix:**
  - Fail fast only on partial config (one of url or key present). When both are blank, register a `ObjectStorage` that throws a typed `StorageUnavailableException`, so the service maps it to 503.
  - Add an explicit "Cross-plan dependency" section naming which plan edits compose and config-repo, and make it a precondition in `blocks`.
  - Support key rotation through a supplier, or document that a restart is required.

## Finding 4: byte[] API plus 10 MB Speaking uploads against 512 MB heaps is a service-wide OOM risk, and the "check size before reading" mitigation does not exist in the multipart path
- **Severity:** High
- **Location:** Plan.md "Rủi ro" row about `byte[]` RAM. Phase 1 design note "put nhận byte[]". Phase 2 `UploadPolicy.requireSize` ("trước khi đọc body").
- **Flaw:**
  - The mitigation is "`UploadPolicy.maxBytes` checks before reading the whole file".
  - A multipart upload is already parsed and spooled by the container before the controller runs.
  - The in-memory copies per request multiply: `MultipartFile.getBytes()`, a `put(byte[])` copy, and the JDK `BodyPublishers.ofByteArray`.
  - Nothing bounds concurrency or total in-flight bytes.
  - Spring's default `spring.servlet.multipart.max-file-size` is 1 MB, so the 2 MB and 10 MB limits fail unless each service raises it. No plan item tells services this.
  - The repo has no multipart code at all, so this is a net-new, unproven path.
- **Failure scenario:** a class of learners submits Speaking recordings near the exam deadline.
  - 10 MB × 3 copies × 20 concurrent uploads is about 600 MB of heap against `-Xmx512m`.
  - assessment-service hits OOM, which takes down all exams and results with it.
- **Evidence:**
  - `docker-compose.yml:23` (`JAVA_TOOL_OPTIONS: "-Xms64m -Xmx512m"`).
  - `grep MultipartFile|multipart` over `services/*/src/main` returned no matches, so there is no precedent.
  - Plan.md line 33 (limits 2 MB and 10 MB).
- **Suggested fix:**
  - Add a concurrency limit (semaphore or bulkhead) to the `put` path, or accept `InputStream` with a known length for `RestClient`.
  - Cap the Speaking limit relative to heap, or record the per-service multipart settings as a required checklist.
  - Say clearly that `requireSize` is only a pre-check for the `Content-Length` header.

## Finding 5: "readTimeout 10s" on the JDK client bounds the whole upload, so large puts time out after Supabase may already have stored the object. A non-idempotent timeout leaves the caller blind.
- **Severity:** High
- **Location:** Phase 3 "Dựng RestClient" (`JdkClientHttpRequestFactory`, readTimeout 10s). "Ánh xạ lỗi". "Không retry".
- **Flaw:**
  - UNVERIFIED locally, based on JDK `HttpRequest.Builder.timeout` semantics: the timer covers sending the request and waiting for response headers.
  - A 10 MB body over a slow uplink can exceed 10 seconds, so the call fails with a timeout while the server may still be completing the write.
  - The mapped `StorageException` has `status=0`, indistinguishable from a connection failure where nothing was written.
  - There is no `exists` call (Finding 2), so the caller cannot tell whether to delete a possibly written key.
- **Failure scenario:**
  - A put times out and the caller returns an error to the learner.
  - The object exists in the private bucket, and no DB row references it.
  - The learner retries. The new key is accepted, and the first one is a permanent orphan.
  - The same logic applies to the delete-after-DB-failure path. If `delete` throws `StorageException`, it masks the original exception, because the plan defines no handling for failed cleanup.
- **Evidence:**
  - Phase 3 lines 35 and 62 ("Không retry... caller muốn retry thì sinh key mới").
  - Plan.md "Cấu hình" (`read-timeout` default 10s). The upload size (Plan.md line 33: ≤ 10 MB) is the same order as the timeout, with no scaling by size.
  - Phase 3 Risk table has no row for timeout during upload.
- **Suggested fix:**
  - Use separate timeouts for upload (scaled by size) and for metadata calls.
  - Have `StorageException` expose a typed `outcomeUnknown` flag when the failure happened after the request was sent.
  - Document the cleanup contract: on outcome-unknown, attempt a best-effort `delete(sameKey)`.
  - Add a size-vs-timeout test.

## Finding 7: Error and observability design guarantees silent failures and still leaks Supabase text
- **Severity:** Medium
- **Location:** Phase 3 "Ánh xạ lỗi" and Success Criteria ("module không có logger"). Plan.md rule 4.
- **Flaw:**
  - The message embeds Supabase's `message` field verbatim (≤ 200 chars). Plan.md rule 4 and the test promise that no key or userId appears, but the test only proves this for mock bodies written by the same author.
  - Whether real Supabase error messages ever echo the object path or bucket is UNVERIFIED.
  - The `cause` is dropped intentionally and the module logs nothing. In production, a timeout looks like `storage put failed: bucket=speaking-recordings status=0 message=HttpTimeoutException`. It carries no key, no correlation id and no duration, and the module emits no metric.
  - This defeats the orphan reconciliation that Finding 2 needs: nobody can map a failed put to a key.
- **Failure scenario:** on-call sees a spike of `status=0` errors and cannot tell which users, which bucket operations, or which keys may have been written.
- **Evidence:**
  - Phase 3 lines 58-62.
  - Phase 3 Success Criteria line 128 ("module không có logger (không cần)").
  - Phase 2 Overview uses key and userId as sensitive, but `AGENTS.md` 3.3 (line 101) requires logging and correlation. The plan removes both.
- **Suggested fix:**
  - Let the caller log the key it generated (document this).
  - Return a stable internal error code instead of the raw Supabase message.
  - Optionally emit a Micrometer timer or counter.
  - Add a sanitising step that strips path-like substrings from the Supabase message.

## Flow Tracer: Speaking submission from upload to `audio_reference`

1. Client uploads multipart to a not-yet-existing assessment endpoint, via the Gateway route `/api/assessments/**`.
2. Service runs `UploadPolicy.check`, then `ObjectStorage.put` with a key from `ObjectKeys.forUser("speaking", userId, ext)`.
3. The response goes back to the client, which later posts `POST /api/assessments/submissions` with `audioReference` and `submissionKey` (`LearnerSubmissionController.create`).
4. The use case persists `audioReference` if no row exists for `(user_id, submission_key)`; otherwise it returns the existing row.

**Gaps found:**
- Between steps 2 and 3, no state records the uploaded key server-side, so step 3 relies on the client echoing it (Finding 2).
- A step-3 retry with a new key orphans the second upload.
- Step 2 can time out after the object was written (Finding 5).
